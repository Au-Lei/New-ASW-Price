# 本地任务二：报价去重与更新规则

## 排查结论

旧逻辑仅在报价身份和有效期起止日期均一致时自动选择修订目标；更换有效期会被误判为新增。批次去重也依赖有效期重叠，缺失有效期会漏判。

## 本次规则

- 报价身份：起运港、目的港、船公司、报价来源/协议系列、服务标识、直达/中转、运输路径、费用口径、币种、适用条件。来源系列关联供应商，因此不同代理或协议仍分别保存。服务文本忽略首尾、多余空白及大小写。
- 价格、有效期、船期、航程、备注不是身份字段。匹配唯一同身份报价后，修改原报价并生成新版本，旧版本保留；缺失值继续遵循已有保留原值/显式清空机制。
- 同批同身份、各业务值一致：自动合并发布为一条，保留每一份原件依据。
- 同批同身份、价格或有效期等业务值矛盾：阻止发布并提示双方冲突，人工排除或修改后提交，不自动选取任一价格。
- 不同身份：新增，不能仅按港口删除不同船公司、代理、协议或运输方案的报价。
- 历史已有多笔同身份当前报价：要求明确修订目标，不任意覆盖。不会自动清理历史已发布重复数据。
- 起运港或目的港缺失：仍可按已有规则提交，但不能自动定位并替换旧报价，可显式选择修订目标。
- 并发审批继续检查预览令牌与目标版本，过期提交拒绝发布。

## 验收

API 回归覆盖：价格修改、跨月更换有效期、同港不同来源与方案、缺失有效期去重、跨期冲突、三份重复原件依据合并、历史多候选手动选择、旧版本查询、并发/回滚。
测试使用临时数据库及虚构资料；不调用 AI，不操作本地正式报价或云服务器。
